Part 1 — Project Overview & Architecture
Before writing any code, it helps to see the full picture of what you are building. ContextMesh has three separate pieces that talk to each other. Understanding how they connect will make every step below make sense.

What You Are Building
┌─────────────────────────────────────────────────────┐
│              CONTEXTMESH — 3 PIECES                │
├─────────────────┬──────────────────┬───────────────┤
│   FRONTEND      │    BACKEND       │  MCP SERVER   │
│                 │                  │               │
│ Landing page    │ FastAPI (Python) │ Node.js pkg   │
│ Create team     │ PostgreSQL DB    │ Runs inside   │
│ Login page      │ Redis cache      │ AI tools      │
│ Dashboard       │ LLM pipeline     │ (Cursor, etc) │
│                 │ REST API         │               │
│ React + Vite    │                  │ npm package   │
│ Lovable hosted  │ You host this    │ Team installs │
└─────────────────┴──────────────────┴───────────────┘

How The Three Pieces Talk
// Daily flow once everything is built:

1. Engineer opens Cursor (or Claude Code, Codex, Cline)
   → MCP Server starts automatically
   → MCP calls Backend: GET /master-context?team=acme
   → Backend returns team decisions, work in progress
   → AI session begins WITH team knowledge loaded

2. Engineer works with AI for 2 hours

3. Session ends
   → MCP Server calls Backend: POST /context/save
   → Full chat history saved to PostgreSQL
   → Under this engineer's name + team

4. Every 30 min — aggregation engine runs
   → Reads all team members' recent sessions
   → LLM synthesizes new Master Context
   → Stored in Redis for fast retrieval

5. Engineer opens Dashboard (frontend)
   → Sees team members, their context, Master Context
   → Clicks 'Load into AI' for any teammate
   → Their full context injected into next AI session

Part 3 — Backend Implementation
The backend is the brain of ContextMesh. It stores all the context, handles team authentication, runs the Master Context synthesis engine, and serves everything to the frontend and MCP server via a REST API.
Tech Stack: Python 3.11, FastAPI, PostgreSQL, Redis, LangChain, Anthropic Claude API, ChromaDB. You will run this locally first, then deploy to a simple VPS or Railway.app.

3.2 — Database Schema
There are 4 tables in the database. Here is what each one stores and why.

// db/models.py — Full table definitions

TABLE: teams
  id          → unique team ID (e.g. 'acme-engineering')
  name        → display name (e.g. 'Acme Engineering')
  passcode    → hashed team passcode (never store plain text)
  admin_name  → name of person who created the team
  created_at  → timestamp

TABLE: members
  id          → auto-increment
  team_id     → which team they belong to (FK → teams.id)
  name        → member's display name
  joined_at   → when they joined

TABLE: context_sessions
  id          → auto-increment
  team_id     → which team (FK → teams.id)
  member_name → who this session belongs to
  messages    → full chat history stored as JSON
  files       → list of files mentioned (JSON array)
  decisions   → extracted decisions (JSON array)
  questions   → open questions found (JSON array)
  is_private  → boolean — private sessions hidden from team
  created_at  → timestamp of session

TABLE: master_context
  id          → auto-increment
  team_id     → which team (FK → teams.id)
  content     → synthesized context as JSON
  version     → increment each time it updates
  updated_at  → last synthesis timestamp

3.3 — Authentication API
Two endpoints handle everything related to teams and access. They are simple — no JWT tokens, no OAuth. Just passcode matching.

Endpoint 1 — Create Team
routers/auth.py
// POST /auth/create-team
// Called when admin clicks 'Create Team' on frontend

Request body:
{
  team_name:  'Acme Engineering',
  admin_name: 'Arjun Sharma'
}

What the server does:
  1. Slugifies team name → 'acme-engineering'
  2. Generates passcode → 'MANGO-42-ROCKET'
     (3 random words from a wordlist + 2 random numbers)
  3. Hashes the passcode with bcrypt before storing
  4. Saves to teams table
  5. Saves admin as first member in members table

Response:
{
  team_id:  'acme-engineering',
  passcode: 'MANGO-42-ROCKET',   // plain text, only shown once
  message:  'Team created successfully'
}

Endpoint 2 — Join Team
routers/auth.py
// POST /auth/join-team
// Called when member enters passcode on frontend

Request body:
{
  passcode:    'MANGO-42-ROCKET',
  member_name: 'Priya Mehta'
}

What the server does:
  1. Searches teams table for a matching passcode hash
     (uses bcrypt.checkpw to compare)
  2. If found: adds member to members table
  3. Returns team info so frontend can load the dashboard

Response (success):
{
  team_id:    'acme-engineering',
  team_name:  'Acme Engineering',
  member:     'Priya Mehta',
  all_members: ['Arjun Sharma', 'Priya Mehta', ...]
}

Response (fail):
{
  error: 'Invalid passcode'
  status: 401
}

3.5 — Master Context Engine
This is the most important part of the backend. It is a scheduled job that runs every 30 minutes. It reads all non-private sessions from the team and uses an LLM (Claude) to synthesize them into one Master Context document.

How The Synthesis Works — Step by Step
Scheduler triggers every 30 minutes (or after a new session is saved)
Fetches all non-private sessions for the team from the past 7 days
Groups sessions by member name
Sends everything to Claude API with this prompt:

services/aggregator.py
// services/aggregator.py — The LLM prompt

SYSTEM PROMPT:
You are a technical context synthesizer for an engineering team.
Given multiple AI chat sessions from different team members,
extract and synthesize a clean Master Context.

USER PROMPT:
Here are recent AI sessions from the team:

[MEMBER: Priya Mehta]
Session 1: {messages...}
Session 2: {messages...}

[MEMBER: Arjun Sharma]
Session 1: {messages...}

Return a JSON object with exactly these keys:
{
  decisions: [{ text, made_by, confidence }],
  in_progress: [{ task, member, files }],
  open_questions: [{ question, flagged_by }],
  conflicts: [
    { topic, member_a, says_a, member_b, says_b }
  ]
}

Only include things explicitly mentioned. Do not invent anything.

Claude returns structured JSON
JSON is saved to master_context table with a new version number
Also cached in Redis for fast retrieval (expires in 35 minutes)

Endpoint 6 — Get Master Context
routers/master.py
// GET /master-context?team_id=acme-engineering
// Called by MCP server at start of every AI session
// Also called by frontend right panel

What the server does:
  1. Checks Redis cache first (fast, under 10ms)
  2. If cache miss: reads from master_context table
  3. Returns latest version

Response:

}

3.6 — Conflict Detection
Conflict detection runs as part of the aggregation step. When the LLM synthesizes the Master Context, it is also instructed to find contradictions. But you can add a secondary check too.

services/conflict.py
// services/conflict.py — Additional conflict check

// After synthesis, run this secondary check:
// Take all decisions from current Master Context
// Compare pairwise using embeddings similarity
// If two decisions are about the same topic (similarity > 0.85)
// but say different things → flag as conflict

Example conflicts this catches:
  Decision A (Arjun): 'Rate limit per IP address'
  Decision B (Priya): 'Rate limit per tenant account'
  → Same topic (rate limiting), different approach → CONFLICT

  Decision A (Arjun): 'Use PostgreSQL for main database'
  Decision B (Rahul): 'Use PostgreSQL for persistence'
  → Same topic, compatible statements → NOT a conflict

Part 4 — MCP Server Build
The MCP server is what makes ContextMesh actually work inside AI coding tools. It is a small Node.js package that installs into Cursor, Claude Code, Codex, or any MCP-compatible tool. It runs silently in the background — capturing sessions and injecting context — without the engineer doing anything manually.
Tech: Node.js + TypeScript, @modelcontextprotocol/sdk package. Published as contextmesh-mcp on npm (or installed from GitHub directly).

4.1 — What The MCP Server Does
The MCP server exposes 4 tools to the AI:

TOOL 1: get_master_context
  When: Called automatically at the start of every session
  Does: Fetches current Master Context from backend
  Result: AI session begins knowing what the whole team knows
  Respects: Mode 1 toggle — if OFF, this tool returns empty

TOOL 2: save_context
  When: Called automatically when a session ends
  Does: Sends full chat history to backend /context/save
  Result: Session stored, Master Context scheduled for update

TOOL 3: load_peer_context
  When: Called when engineer says 'load X context' or
        clicks 'Load into AI' button on dashboard
  Does: Fetches named member's full context from backend
  Result: Their history injected into the current session

TOOL 4: mark_private
  When: Called when engineer says 'mark this private' or
        clicks the lock icon on a session card
  Does: Calls backend PATCH /context/session/{id}/private
  Result: Session excluded from Master Context + peer loading

4.3 — The 4 MCP Tools (Code)
Tool 1 — get_master_context
src/tools/getMasterContext.ts
// src/tools/getMasterContext.ts

export const getMasterContextTool = {
  name: 'get_master_context',
  description: 'Fetch the team Master Context — shared knowledge',
  inputSchema: {
    type: 'object',
    properties: {
      team_id: { type: 'string', description: 'Your team ID' }
    },
    required: ['team_id']
  },
  handler: async ({ team_id }) => {
    // Check if Mode 1 toggle is ON (stored in local config)
    if (!config.masterContextEnabled) return { context: null };

    const response = await api.get(`/master-context?team_id=${team_id}`);
    return { context: response.data };
  }
};

Tool 2 — save_context
src/tools/saveContext.ts
// src/tools/saveContext.ts

export const saveContextTool = {
  name: 'save_context',
  description: 'Save the current AI session to team context',
  inputSchema: {
    type: 'object',
    properties: {
      team_id:        { type: 'string' },
      member_name:    { type: 'string' },
      messages:       { type: 'array' },   // full chat history
      files_modified: { type: 'array' },   // files touched
      is_private:     { type: 'boolean' }  // default false
    },
    required: ['team_id', 'member_name', 'messages']
  },
  handler: async (params) => {
    const response = await api.post('/context/save', params);
    return { saved: true, session_id: response.data.session_id };
  }
};

Tool 3 — load_peer_context
src/tools/loadPeerContext.ts
// src/tools/loadPeerContext.ts

export const loadPeerContextTool = {
  name: 'load_peer_context',
  description: 'Load a teammate context into current AI session',
  inputSchema: {
    type: 'object',
    properties: {
      team_id:     { type: 'string' },
      member_name: { type: 'string', description: 'Whose context to load' }
    },
    required: ['team_id', 'member_name']
  },
  handler: async ({ team_id, member_name }) => {
    const response = await api.get(
      `/context/member?team_id=${team_id}&member=${member_name}`
    );
    // Returns full chat history + decisions for that member
    return { peer_context: response.data };
  }
};

Tool 4 — mark_private
src/tools/markPrivate.ts
// src/tools/markPrivate.ts

export const markPrivateTool = {
  name: 'mark_private',
  description: 'Mark the current or a specific session as private',
  inputSchema: {
    type: 'object',
    properties: {
      session_id: { type: 'number' }
    },
    required: ['session_id']
  },
  handler: async ({ session_id }) => {
    await api.patch(`/context/session/${session_id}/private`,
      { is_private: true }
    );
    return { marked_private: true, session_id };
  }
};

The CONTEXTMESH_API value points to wherever your backend is running. During development this is localhost:8000. When you deploy the backend to Railway or a VPS, replace with the public URL.

Part 5 — Connecting Frontend + Backend + MCP
Once all three pieces are built separately, here is exactly how to wire them together so they talk to each other correctly.

5.1 — Frontend → Backend Connection
Replace all localStorage logic in the Lovable frontend with real API calls to the backend. These are the exact swaps to make:

src/api.js — add to your Lovable project
// BEFORE (localStorage only):
const team = JSON.parse(localStorage.getItem('team'));

// AFTER (real backend):
const response = await fetch('http://localhost:8000/auth/join-team', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ passcode, member_name })
});
const team = await response.json();
localStorage.setItem('currentUser', JSON.stringify(team)); // keep for session

// Replace every localStorage data call with a fetch() to the API
// Create a src/api.js file in your Lovable project:

export const API = 'http://localhost:8000'; // change when deployed

export const createTeam = (teamName, adminName) =>
  fetch(`${API}/auth/create-team`, { method:'POST',
    headers:{'Content-Type':'application/json'},
    body: JSON.stringify({ team_name: teamName, admin_name: adminName }) })
  .then(r => r.json());

export const joinTeam = (passcode, memberName) =>
  fetch(`${API}/auth/join-team`, { method:'POST',
    headers:{'Content-Type':'application/json'},
    body: JSON.stringify({ passcode, member_name: memberName }) })
  .then(r => r.json());

export const getMasterContext = (teamId) =>
  fetch(`${API}/master-context?team_id=${teamId}`).then(r => r.json());

export const getMemberContext = (teamId, memberName) =>
  fetch(`${API}/context/member?team_id=${teamId}&member=${memberName}`)
  .then(r => r.json());

5.2 — MCP Server → Backend Connection
The MCP server connects to the backend through the api.ts file. Here is the complete shared API helper:

src/api.ts
// contextmesh-mcp/src/api.ts

import axios from 'axios';

const BACKEND_URL = process.env.CONTEXTMESH_API || 'http://localhost:8000';

export const api = axios.create({
  baseURL: BACKEND_URL,
  timeout: 10000,
  headers: { 'Content-Type': 'application/json' }
});

// Helper: read config from environment variables
export const config = {
  teamId:               process.env.TEAM_ID || '',
  memberName:           process.env.MEMBER_NAME || '',
  masterContextEnabled: process.env.MASTER_CONTEXT_ENABLED !== 'false',
};
